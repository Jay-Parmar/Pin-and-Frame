# TravelMap handoff (2026-11-22)

This consolidates a Claude Code session (2026-11-21 to 2026-11-22) so the work can continue in Codex on another PC. Four research agents verified the facts against official docs on 2026-11-21. Details and sources are in `docs/research/`.

## 1. What the user wants
Their request, condensed (the full text is in `conversation.md`):
- An app showing the places they travel to, with a consolidated photo collection for each place.
- A map where the places display along a timeline.
- Photos are on Instagram and on their phone.
- They have no storage server. They want it free and viewable later, without worrying about storage or deployment.
- They have a Google account with 15 GB and thought of using it through Firebase.
- They believed Vercel and Render free apps "reset on 30 days" and asked to be corrected if wrong.

## 2. Corrections given
- **Vercel doesn't reset.**
  - The current production deployment is never deleted, on any plan. The 30-day retention only removes older deployments that have been replaced.
  - The free Hobby plan is for personal, non-commercial use. Its free file storage (Blob) is 1 GB, which is too small for photos.
- **Render: the user is right about 30 days, but only for the free Postgres database.** It expires 30 days after creation and is deleted after a further 14-day grace period. Free web services also:
  - spin down after 15 minutes without traffic and take about a minute to wake;
  - lose local files on every restart, redeploy or spin-down;
  - share 5 GB/month of outbound bandwidth.
- **Firebase can't use the 15 GB.**
  - That quota is shared by Gmail, Drive and Google Photos, and it's separate from Firebase.
  - Since 2026-02-03, Firebase Storage needs the Blaze plan, which requires a card. Its no-cost part is 5 GB stored and 100 GB/month downloaded, in three US regions only.
  - Drive can't reliably serve images to a website either. Google broke direct image links in 2024, and the workarounds get throttled.

## 3. Findings that shape the design more than hosting does
- **Instagram:**
  - Personal accounts get no API access, and even the business API exposes no location.
  - Use the "Download your information" export in JSON. It contains photos (about 1440 px, all EXIF stripped), captions and post dates.
  - Only some posts carry GPS (`media_metadata.photo_metadata.exif_data`), and the current format has no place names.
  - Most Instagram photos will need their location matched by date against phone photos, or set by hand.
- **Phone and Google Photos:**
  - Location survives only in originals copied over USB, or in Google Takeout (files plus JSON sidecars with `geoData` and `photoTakenTime`).
  - The Google Photos Picker API strips GPS, and iOS and Android usually strip it from browser uploads.
- **Consequence:** photo import should be a batch job on the PC, not uploads from the phone.

## 4. Recommendation given (pending the user's confirmation)
A static website plus an import script, on Cloudflare's free tier:

| Piece | Choice | Free limit |
|---|---|---|
| Website | Cloudflare Workers (static assets) | Static requests free and unlimited; never sleeps or expires |
| Photos | Cloudflare R2 | 10 GB-month, free egress; about 20,000 web-sized photos. Served through the Worker, which allows 100k requests/day |
| Trips and places data | One JSON file written by the import script | No database to expire |
| Map | MapLibre GL JS + OpenFreeMap tiles | Free, no account or API key |
| Privacy | Cloudflare Access with Google login or an emailed one-time PIN | Up to 50 users; works on workers.dev, so no domain needed |

- Originals stay in Google Photos or the phone backup. The site holds web-sized copies of about 0.5 MB each.
- A script on the PC reads each photo's location and date and groups photos into trips and places. It then makes the copies, uploads them and redeploys the site.
- **Catch:** R2 and Access ask for a card on file.
  - It's $0 within the free limits.
  - R2 overage bills automatically, with no hard cap. The Standard storage list price is about $0.015/GB-month (not re-verified this session).
  - Set a budget alert.
- **No-card fallback:**
  - Keep the photos inside the website itself as Workers static assets. The limits are 20,000 files per version and 25 MiB per file, with no documented total size.
  - That fits about 9,000 photos with a thumbnail each, and it's the same app.
  - Privacy would then need something other than Access, because Access setup also asks for payment details.

## 6. Open question (last thing asked) and stated assumptions
**How will you add photos?**
1. **After each trip, from the PC (recommended).** Copy phone photos over USB or from a Takeout download, add the Instagram export and run one command. Locations and dates stay intact, and there's no server or login to maintain.
2. **From the phone while traveling.** This needs an upload page with a login and a small backend. Phones strip location from uploads, so each batch needs its place tapped on the map, or the phone's current location used.

Starting with option 1 and adding option 2 later is possible.

**Assumptions stated for the user to correct:**
- A card on file is OK.
- The site is private to the user and people they invite.

The user hasn't answered yet; their next message asked for this handoff.

## 7. Draft design sketch (Claude's proposals; not discussed or approved)
These ideas are for the next agent to raise with the user, not to build from.

**Import pipeline (runs on the PC)**
1. Inputs: a folder of phone originals (USB copy) or an extracted Google Takeout, plus the Instagram JSON export.
2. Read date and location:
   - Phone originals: EXIF `DateTimeOriginal` (plus `OffsetTimeOriginal` when present) and GPS.
   - Takeout: the sidecar's `photoTakenTime` and `geoData`/`geoDataExif` (0.0 means no location). Pair sidecars to files by the JSON `title`, not the filename (see the quirks in the research doc).
   - Instagram: caption, `creation_timestamp` (when posted, not when taken) and `exif_data` latitude/longitude when present.
3. Fill gaps. An Instagram post without GPS gets the location of the phone photo with GPS nearest in time. If there's none, mark the post "needs a place" for the user to tag in a small review step.
4. Group:
   - Split photos into trips by time gaps.
   - Cluster photos into places by distance.
   - Name places by reverse geocoding, using either an offline city dataset or a rate-limited geocoder called once per cluster and cached.
5. Make web copies:
   - A display size (around 2048 px on the long edge, WebP or AVIF) plus a thumbnail (around 400 px).
   - Strip EXIF from the copies.
   - Name files by content hash, so re-runs skip duplicates and the files can be cached permanently.
6. Upload new files to R2, write the JSON data file and deploy the site.
7. Keep a local manifest so each run only processes new photos.

**Things to check when building**
- iPhone originals are HEIC, so the image library must decode HEIC. sharp's prebuilt binaries reportedly don't; Python's pillow-heif does. Verify this.
- Time zones. Takeout's `photoTakenTime` is UTC without an offset, and EXIF times are often local time without an offset. Derive local time from the coordinates so the timeline is in the right order.
- Videos would use up the 10 GB quickly. Suggest photos only for the first version.
- If the site is ever public, leave out photos taken near home and keep EXIF stripped from the web copies.

**Site (UI idea)**
- A full-screen map with clustered pins, a timeline scrubber (years, then trips) and a trip list.
- Picking a trip draws its route in time order and filters the pins.
- Clicking a place opens its gallery: thumbnails that open full size in a lightbox.

**Data file shape (idea)**
- `trips`: id, title, start, end, place ids.
- `places`: id, name, country, lat, lng, first visit, photo count.
- `photos`: id (hash), taken-at time with offset, lat, lng, place id, trip id, source (phone or Instagram), caption, width, height, display and thumbnail paths.
